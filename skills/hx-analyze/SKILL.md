# 초기 분석

지금은 초기 분석 단계다. **코드·설정·의존성을 바꾸지 않는다.** 결과는 대화로 보고하고, 요구사항 문서(REQUIREMENTS.md 또는 과제 지정 문서)에만 기록한다.

## 1. 읽는 순서
1. 과제 안내, 시험 규정, 적용되는 AGENTS.md 등 작업 규칙
2. README와 연결된 요구사항·설계 문서
3. 프로젝트 구조, 의존성 선언, 실행·빌드·테스트 명령
4. 과제와 관련된 진입점, 주요 코드, 테스트, TODO, 데이터 파일(앞부분과 스키마만)

전체 파일을 무작정 읽지 않는다. `rg`, `ls`, 줄 범위로 과제와 직접 관련된 경로부터 본다. 비밀정보 값은 출력하지 않는다.

## 2. 사실과 요구사항 구분
아래 네 가지를 따로 정리하고, 각 항목에 파일 경로와 가능하면 줄 번호를 붙인다.
- **명시된 요구사항**: 문서가 직접 요구한 기능·제약·제출물·완료 조건
- **현재 구현**: 코드가 실제로 하는 동작
- **기존 테스트의 기대 동작**: 테스트가 검증하는 조건
- **차이와 불확실성**: 미구현·충돌·누락·확인이 필요한 점

현재 코드나 테스트의 동작을 곧바로 최종 업무 요구사항으로 단정하지 않는다. 추정은 `(추정)`으로 표시한다. 가이드·예시 화면의 앱 종류나 파일명으로 과제 유형을 짐작하지 않는다.

## 3. 핵심 기능 후보와 대표 사용 흐름
요구사항 목록과 별도로, **이 서비스가 결국 무엇을 해 주는가**를 정리한다. README가 짧고 핵심 요구가 담당자에게 있을 수 있으므로, 저장소의 힌트로 후보를 세우고 확인할 것을 분명히 한다.
- 힌트를 찾을 곳: README의 목적·동사 문장("~를 확인하고 싶다", "~를 줄이고 싶다"), 라우트·API·CLI 이름, 빈 함수·TODO, 기존 테스트 이름, 데이터 열, 화면 틀(버튼·입력칸·메뉴).
- **대표 사용 흐름 한 줄**: `누가 → 무엇을 넣고 → 어떤 결과를 보고 → 무엇을 결정·행동한다`. 후보가 둘 이상이면 각각 쓴다.
- **핵심 기능 후보 1~3개**: 각각 `기능 / 근거(파일:줄) / 확정·추정 / 이게 틀리면 무엇이 달라지나`.
- `확정`은 문서에 명시된 것만이다. 코드 뼈대·테스트·데이터에서 추론한 것은 모두 `추정`이다.
- 이 흐름이 이후 계획의 최소 실행 흐름(MVP) 후보가 된다. 여기서 핵심 기능을 임의로 정하거나 추가 기능을 덧붙이지 않는다.

## 4. 담당자 질문 고르기
문서와 코드에서 답을 찾을 수 있는 것은 먼저 조사한다. 그 뒤 **담당자만 결정할 수 있고 구현 방향이나 검증 기준을 바꾸는** 질문을 우선순위순으로 최대 5개 만든다.

**1순위는 항상 핵심 기능 확인이다.** 3단계의 대표 사용 흐름이나 핵심 기능 후보에 `추정`이 하나라도 있으면, 첫 질문으로 그것을 확인한다. 가설을 그대로 보여 주고 맞는지, 무엇이 더 중요한지 묻는다.
- 예: "제 이해로는 [누가] [무엇을 넣고] [어떤 결과]를 보고 [무엇을 결정]하시려는 것 같은데 맞을까요? 오늘 꼭 되어야 하는 건 [A]와 [B] 중 어느 쪽인가요?"
- 후보가 모두 `확정`이면 1순위를 생략하고, 경계 사례·성공 기준 질문부터 고른다.

각 질문에는:
- 담당자에게 바로 보낼 짧은 질문 (비개발자가 이해할 말, 가능하면 "제 이해로는 A인데 맞을까요?"처럼 가설이나 선택지 포함)
- 질문하게 된 근거와 확인되지 않은 점
- 답에 따라 달라지는 구현 또는 검증 기준

단순 기술 선택(언어·프레임워크·DB)이나 이미 명시된 내용은 묻지 않는다. 물을 업무 질문이 없으면 만들지 않는다. 질문은 초안만 쓰고, 메신저나 화면을 조작해 보내지 않는다.

## 5. 첫 보고 형식
- A. 과제 목표와 필수 제출물 요약
- B. 확인된 요구사항과 근거
- C. 현재 구현·테스트와 요구사항의 차이
- D. 핵심 기능 후보와 대표 사용 흐름 (확정·추정 표시)
- E. 담당자에게 물을 질문 (추정이 있으면 1번은 핵심 기능 확인)
- F. 답을 기다리지 않고 진행할 수 있는 작업
- G. 답 전에는 결정하면 안 되는 사항
- H. 실행·검증 명령과 아직 실행하지 않은 항목

5~10분 안에 첫 보고를 한다. 범위가 크면 다 끝내려 기다리지 말고 확인된 것과 미확인을 나눠 먼저 보고한다. 테스트는 실행 여부를 정확히 표시하고, 실행하지 않았으면 통과라고 말하지 않는다. 외부 서비스 호출·설치·데이터 변경이 필요한 확인은 먼저 알린다.

## 6. 기록
보고 후 요구사항 문서에 B·D·E·G를 기록한다. D는 `핵심 기능과 대표 흐름` 절에 둔다. 과제 지정 문서가 없으면 `templates/REQUIREMENTS.md` 형식으로 작업 폴더 루트에 REQUIREMENTS.md를 만든다. 이미 있으면 갱신만 한다.

시험 규정이 이 지시보다 우선한다. 후속 서술형 단계에서는 이 스킬을 쓰지 않는다.
