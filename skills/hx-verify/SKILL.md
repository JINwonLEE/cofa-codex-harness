# 실행 증거로 검증

범위를 지정하지 않으면 최근 변경과 관련된 요구사항을 검증한다. 설명보다 과제 안내, 실제 파일, 실행 결과를 먼저 본다. `만들었음`, `실행됨`, `요구를 충족함`을 구분한다. 코드를 읽었거나 파일이 있다는 것만으로 통과라고 하지 않는다.

## 점검 순서 (큰 실패부터)
1. **필수 산출물**: 과제 안내의 파일명·경로·형식과 비교한다. 빈 파일, 임시 문구, 깨진 참조, 실제 결과와 다른 문서를 찾는다.
2. **재현**: 문서에 적힌 실행 명령으로 처음부터 시작되는지 확인한다. 설치 성공과 동작 준비 완료를 구분한다. 외부 서비스나 비밀키가 없으면 안 되는 경로가 핵심 기능에 숨어 있지 않은지 본다.
3. **정확성**: 과제에 영향이 큰 **정상 사례, 경계 사례, 잘못된 입력**을 골라 기대 결과와 대조한다. 기대값은 구현 함수가 아니라 요구사항·담당자 답변·손 계산·원본 집계에서 가져오고 출처를 남긴다. 데이터라면 집계 단위·분모·결측·중복·날짜 경계를, 모델이라면 분할·누수·기준선·지표 의미를 우선 본다.
4. **설계 결정**: DECISIONS.md의 핵심 로직 결정마다 **판별 사례**(버린 대안이면 결과가 달라지는 입력)를 테스트로 실행해, 고른 기준이 실제로 구현됐는지 확인한다. 동점·경계 규칙도 사례로 확인한다. 판별 사례가 기록에 없으면 만들고 기대값의 근거를 남긴다.
5. **설명과 증거**: 문서의 주장마다 실제 파일 위치나 관찰 결과가 있는지 확인한다.

무엇이 가장 위험한 실패인지 분명하지 않으면 시작 전에 사용자에게 한 번 묻는다. 기존 테스트·호출되는 스크립트·훅을 먼저 읽어 UI 자동화나 외부 전송이 없는 허용된 검사만 실행하고, 없으면 핵심 규칙을 확인하는 최소 테스트를 추가한다. 바뀌지 않은 통과 항목은 다시 돌리지 않는다. 관련 코드·설정이 바뀌면 영향받는 검증만 다시 한다.

## 화면이 있는 결과물
- 서버가 `0.0.0.0`에 바인딩됐는지, 실제 포트에서 `curl`로 응답하는지 확인한다.
- 사용자에게 플랫폼 Browser에 넣을 포트·경로와 직접 눌러 볼 동작 2~3개(핵심 입력·버튼·오류 상황)를 짧게 안내하고 서버 터미널을 유지하게 한다.
- 사용자가 확인했다고 말하기 전의 화면 항목은 `미실행`이다.
- 외부 터널, Computer Use, Playwright·Selenium·브라우저 MCP 같은 UI 자동화는 쓰지 않는다.

## 실패했을 때
가장 작은 실패 사례를 재현한다 → 오류와 최근 변경을 확인한다 → 구체적인 원인 하나를 검증한다 → 최소 범위로 고친다 → 그 사례와 영향받는 검증을 다시 실행한다. 기준을 낮춰서 통과시키지 않는다. 같은 방법을 새 근거 없이 반복하지 않는다. 약 10분이 지나면 멈추고 선택지를 보고한다.

## 기록과 보고
PLAN.md 검증 결과 표에 `요구 ID / 명령 또는 수동 확인 / 기대값 / 실제 결과 / 판정 / 확인한 사람`을 남긴다. 판정은 **통과 / 실패 / 미실행** 셋뿐이다. 시간 부족·접근 불가도 이유와 함께 미실행으로 남긴다. 로그·수치·테스트 성공을 만들어내지 않는다.

보고는 세 묶음으로 짧게:
- **제출 전 수정 필요**: 필수 조건 실패, 실행 불가, 잘못된 결과, 누락 파일
- **확인됨**: 요구사항, 실행한 방법, 관찰 결과
- **아직 확인 안 됨**: 이유와 남은 확인 방법

후속 서술형 단계에서는 이 스킬을 쓰지 않는다.
