# 업무 담당자 인터뷰

`check`는 보내기 전 질문 점검, `record`는 받은 답 기록이다. 접두사가 없어도 질문 초안인지 받은 답인지 분명하면 그 작업을 한다. 요구사항 문서의 관련 항목과 기존 답변만 읽는다.

## check
- 이미 받은 답, 문서에 있는 내용, 중복, 막연한 질문, 한 문장에 섞인 여러 질문을 걸러낸다.
- **지금 구현이나 검증에 영향을 주는 질문을 한 번에 최대 3개** 고른다. 우선순위는 `틀렸을 때 손실 × 영향 범위`로 판단한다. 요구사항 문서의 `핵심 기능과 대표 흐름`에 `추정`이 남아 있으면 **그 확인을 1번 질문**으로 둔다.
- 바로 보낼 수 있게 짧게 다듬는다. 비개발자가 이해할 말로 쓰고, 가능하면 가설이나 선택지를 붙인다.
  - 예: "이 결과는 누가 어떤 결정을 할 때 보나요?"
  - 예: "[규칙]을 [A]로 이해했습니다. [경계 사례]도 같나요, 아니면 [B]인가요?"
  - 예: "[잘못된 입력]이 들어오면 그 항목만 빼나요, 전체를 멈추나요?"
- 실제 입력 예시나 기대 결과 예시를 요청하면 답이 분명해지는지 본다.
- 질문 수를 채우려고 새 질문을 만들지 않는다. 기술 선택은 묻지 않는다. 전송은 사용자가 직접 한다.
- **라운드 수 제한은 없다.** 답을 듣고 새 갈래가 생기거나, 구현·검증 중 새로 모르는 점이 생기면 언제든 다시 `check` → 사용자 전송 → `record`를 반복한다. 후속 질문은 정상적인 반복 개선이다.
- 대신 매 라운드는 **지금 구현이나 검증을 막는 질문**만 고른다. 영향이 작은 항목은 가정으로 표시하고 진행하며, 나중에 묶어서 묻는다. 같은 내용을 표현만 바꿔 다시 묻지 않는다.
- 후속 질문에는 이전 답을 짧게 인용해 맥락을 붙인다. 예: "앞서 환승이 적은 경로가 우선이라고 하셨는데, 환승 횟수도 같으면 더 빠른 쪽을 보여드리면 될까요?"

## record
- 받은 답을 요구사항 문서의 답변 표에 기록하고, 관련 Must·가정·미해결 항목을 갱신한다. 중요한 원문만 짧게 인용하고, 없던 답이나 시각을 만들지 않는다.
- 답으로 범위·핵심 규칙·기대값이 바뀌면 DECISIONS.md에 기록한다.
- 핵심 기능·대표 흐름에 대한 답이면 해당 행을 `확정`으로 바꾸거나 고치고, 바뀐 핵심 기능을 먼저 알린다.
- 업무 규칙은 `입력 → 기대 결과` 확인 사례로 바꿔 기준 사례에 추가한다.
- 담당자가 묻지 않은 정보를 덧붙였다면 숨은 요구일 수 있으니 요구사항 후보로 표시한다.
- 답에서 새로 생긴 질문이 있으면 `후속 질문 후보`로 바로 제시한다(지금 막히는 것 / 나중에 물어도 되는 것 구분). 없으면 만들지 않는다.
- 구현·테스트·계획에 미치는 영향을 3줄 이내로 알린다. 답 기록만 요청받았으면 기록과 영향 보고에서 멈춘다.
- 담당자 답이 과제 안내의 필수 조건이나 공식 규칙과 충돌하면 둘 다 충족했다고 쓰지 않고 사용자에게 알린다.

후속 서술형 단계에서는 이 스킬을 쓰지 않는다.
