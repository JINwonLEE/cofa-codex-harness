# 막혔을 때: 고치기 전에 원인부터

이 세션에 하네스 작업 규칙(`작업 규칙 (Codex)`)이 적용돼 있지 않으면 먼저 `hx-analyze` 스킬 폴더의 `RULES.md`를 읽고 따른다(과제 안내·기존 지침 우선).

**원인을 확인하기 전에는 고치지 않는다.** 시간에 쫓길수록 추측 수정이 시간을 더 잡아먹는다. 시작할 때 시각을 기억하고, **약 10분이 지나면 멈추고 보고**한다.

## 1. 실패 신호 만들기 (가장 중요)
이 버그에서만 빨간불이 들어오는 **명령 하나**를 먼저 만든다. 순서대로 시도한다.
1. 해당 지점을 겨냥한 실패 테스트
2. 실행 중인 서버에 대한 `curl`
3. 고정 입력으로 CLI·스크립트를 실행해 기대 출력과 비교

이 명령을 실제로 한 번 실행해 사용자가 말한 증상이 그대로 나오는지 확인한다. 근처의 다른 실패면 틀린 버그다. 신호를 만들 수 없으면 시도한 것을 적고 멈춰서 사용자에게 필요한 정보(재현 순서, 오류 원문, 입력 예시)를 요청한다. 화면을 자동 조작하는 재현(Playwright 등)은 쓰지 않는다. 화면 증상은 사용자가 직접 확인한 내용을 받는다.

## 2. 사실 모으기
- 오류 메시지와 스택 트레이스를 끝까지 읽는다. 파일·줄·오류 코드를 적는다.
- 최근 변경을 본다: `git diff`, `git log -3 --stat`, 새 의존성, 설정.
- 재현을 가장 작은 경우로 줄인다. 입력·단계를 하나씩 빼며 빨간불이 유지되는지 본다.
- 비밀값이 나오는 출력은 `<REDACTED>`로 가린다.

## 3. 가설 세우고 하나씩 확인
- 가능성 높은 순으로 가설 2~3개를 적는다. 각 가설에 `X가 원인이면 Y를 바꿨을 때 사라진다` 같은 예측을 붙인다.
- 가설 목록을 사용자에게 짧게 보여 준다. 사용자가 이미 아는 사실로 순서가 바뀔 수 있다. 답을 기다리느라 멈추지는 않는다.
- 한 번에 변수 하나만 바꾼다. 임시 로그에는 `[DEBUG-hx]` 같은 접두사를 붙인다.

## 4. 고치고 확인
1. 가능하면 줄인 재현을 회귀 테스트로 만들고 실패하는 것을 본다.
2. 원인에 대한 최소 수정을 한다. 관련 없는 정리·리팩터링을 섞지 않는다.
3. 테스트와 1단계의 원래 신호가 통과하는지 다시 실행한다. 영향받는 기존 검증도 다시 돌린다.
4. `[DEBUG-hx]` 로그를 지운다(`rg 'DEBUG-hx'`로 확인).
5. 원인과 수정 내용을 커밋 메시지에 한 줄로 남기고, 결과에 영향을 준 실패였다면 PLAN.md에 기록한다.

같은 방법이 두 번 실패하면 새 근거 없이 세 번째로 반복하지 않는다. 기준을 낮추거나 테스트를 지워서 통과시키지 않는다.

## 5. 미리보기·서버가 안 뜰 때
순서대로 확인한다: 서버 프로세스가 살아 있는지와 터미널 오류 → 실제 실행 포트 → `0.0.0.0` 바인딩 여부(`localhost`만이면 안 보일 수 있음) → 경로(`/`부터) → 서버 쪽 `curl` 응답. 외부 터널을 만들지 않는다. 플랫폼 자체 오류로 보이면 발생 시각·단계·직전 동작·오류 문구를 정리해 사용자가 문제 신고를 하도록 안내하고, 독립된 작업을 계속한다.

## 6. 10분 보고 형식
`증상 / 지금까지 확인한 것 / 가장 유력한 원인과 근거 / 선택지: 계속 조사(예상 시간) · 우회 · 범위 조정`. 핵심 경로를 막는지 먼저 밝힌다. 해결하지 못한 Must를 완료로 표시하지 않는다.

후속 서술형 단계에서는 이 스킬을 쓰지 않는다.
