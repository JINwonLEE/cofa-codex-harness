# 핵심 로직 설계: 고르고, 이유를 남기고, 증명할 사례를 만든다

후속 질문은 "왜 이 방법이었나, 다른 방법은 왜 버렸나, 이 경우엔 어떻게 되나"를 묻는다. 이 스킬의 목적은 **사용자가 직접 고르고 설명할 수 있는 설계 결정**을 남기는 것이다. Codex가 대신 정하고 코드 속에 숨기지 않는다.

**쓸 때**: 같은 요구사항을 서로 다른 결과로 구현할 수 있는 로직을 만들기 직전. 예: 경로·추천·배정·스케줄·랭킹·매칭·판정·집계 기준, 그래프·트리·캐시 같은 자료구조, 데이터 모델, 외부 라이브러리 사용 여부.
**쓰지 않을 때**: 결과가 달라지지 않는 단순 CRUD·화면 배치·변수명 같은 선택. 그런 것은 가정으로 기록하고 진행한다.

## 1. 결정할 문제 정의 (코드 수정 없음)
- 무엇을 정하는가: 한 문장. 예: "출발역→도착역 경로 하나를 고르는 기준과 방법"
- 관련 요구 ID와 담당자 답변. 요구사항에 기준이 없으면 그 자체가 담당자 질문이다(`$hx-interview`). 업무 기준(무엇이 더 좋은 결과인가)은 사용자·담당자가 정하고, 그 기준을 만족하는 기술 방법은 함께 고른다.
- 입력 규모와 제약: 데이터 크기, 응답 시간, 실행 환경. 복잡도 판단의 근거로 쓴다.

## 2. 선택지 2~3개 비교
각 선택지를 같은 항목으로 비교하고 표로 보여 준다.

| 항목 | 선택지 A | 선택지 B | (C) |
|---|---|---|---|
| 방법 한 줄 (모델링·알고리즘) | | | |
| 요구사항 충족 (요구 ID별) | | | |
| 결과가 어떻게 달라지는가 | | | |
| 시간·공간 복잡도 (입력 규모 기준) | | | |
| 구현 시간·위험 | | | |
| 틀리는 조건·한계 | | | |

- 실제로 고려할 만한 것만 넣는다. 들러리 선택지를 만들지 않는다.
- 추천안이 있으면 이유와 함께 표시하되, **결정은 사용자가 한다.**

예시 (노선 탐색이라면):
- 모델: 역=노드, 구간=간선(소요 시간), 환승=같은 역의 노선 간 간선(환승 시간 또는 패널티)
- 기준: 최소 시간 / 최소 환승 / 최소 요금 / 여러 기준을 사전식 비교(환승 수 → 시간)하거나 가중합
- 방법: 가중치 없음 → BFS, 음수 없는 가중치 → 다익스트라, 여러 기준 → 기준을 튜플로 비교하는 다익스트라, 상위 k개 경로 → k-최단경로
- 경계: 같은 역 출발·도착, 경로 없음, 동점, 순환, 운행 시간·중단 구간

## 3. 판별 사례 만들기 (가장 중요)
**선택지마다 결과가 달라지는 작은 입력**을 최소 1개 만든다. 예: "경로 X는 환승 1회·40분, 경로 Y는 환승 0회·55분 → 최소 시간이면 X, 최소 환승이면 Y."
- 이 사례의 기대 결과를 손으로 계산해 적는다. 나중에 `$hx-verify`가 이 사례로 **고른 기준이 실제로 구현됐는지** 확인한다.
- 동점 처리 규칙과 그 사례, 경계 조건별 기대 동작(빈 결과·오류·메시지)도 정한다. 결과가 매번 같도록(결정적) 동점 기준을 명시한다.

## 4. 결정 기록 (사용자가 고른 뒤)
DECISIONS.md(또는 과제 지정 문서)에 아래 형식으로 남긴다. 사용자가 고르지 않았으면 `결정 대기`로 두고 구현하지 않는다.

```
## D-xx. [결정 제목]
- 결정: [고른 방법] (사용자 선택, 시각)
- 이유: [요구 ID·담당자 답변·제약]
- 버린 대안과 이유: [B — 왜 아닌지], [C — 왜 아닌지]
- 복잡도: [시간/공간, 입력 규모 n·m 기준]
- 판별 사례: [입력 → 기대 결과], 동점 규칙: [...]
- 경계 조건: [경우 → 기대 동작]
- 틀리는 조건·한계: [...]
- 검증: PLAN.md 검증 결과의 해당 행
```

사용자가 Codex 추천을 바꾸거나 거절했다면 그 사실과 이유도 적는다. 하지 않은 판단을 사용자가 했다고 쓰지 않는다.

## 5. 구현 중 새 선택이 생기면
구현하다가 결과를 바꾸는 선택(기준 변경, 근사·휴리스틱 도입, 라이브러리 교체, 성능 때문에 정확도 포기)이 새로 생기면 **멈추고** 이 스킬의 2~4단계를 짧게 반복한다. 조용히 바꾸지 않는다. 외부 코드·라이브러리를 쓰면 출처와 사용 범위를 기록하고, 핵심 로직을 통째로 대체하지 않는다.

## 6. 보고
`결정할 것 / 선택지 표 / 판별 사례 / 추천과 이유 / 사용자가 정할 것`을 짧게 보고하고 사용자 선택을 기다린다. 선택 뒤에는 기록하고 구현으로 넘어간다.

후속 서술형 단계에서는 이 스킬을 쓰지 않는다.
