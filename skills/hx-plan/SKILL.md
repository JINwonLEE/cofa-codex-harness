# 계획

요구사항 문서와 기존 PLAN.md, DECISIONS.md만 읽는다. 없는 사실은 `확인 필요`로 표시한다. 과제가 계획 문서 이름이나 양식을 지정했으면 그것을 쓴다. 없으면 `templates/PLAN.md` 형식으로 작업 폴더 루트에 PLAN.md를 만든다.

## 작성할 내용
1. **시간 기준**: 사용자에게 받은 시작 시각·마감 시각(또는 남은 시간), `기능 동결 = 마감 30분 전`, `제출 시작 = 마감 10분 전`.
2. **최소 실행 흐름(MVP)**: 요구사항 문서의 `대표 흐름`을 그대로 쓴다. 대표 입력 하나가 의미 있는 결과 하나로 이어지는 가장 작은 경로이며, 가능한 한 앞쪽에서 완성한다. 대표 흐름이 아직 `추정`이면 그 사실을 계획에 표시하고 사용자에게 알린다.
3. **작업 목록**: 작고 독립적으로 검증 가능한 단위로 나눈다. 각 작업에 다음을 붙인다.
   - 관련 요구 ID
   - 완료 기준 (관찰 가능한 결과)
   - 확인 방법 (명령·입력과 기대값)
4. **Must와 Should 구분**: Must를 모두 추적한다. 시간이 남으면 할 일은 Should로 둔다.
5. **이번에 하지 않을 것**과 그 이유.
6. **주요 위험**: 막히면 큰 손해가 나는 지점과 대안.
7. **설계 결정이 필요한 작업**: 결과를 바꾸는 핵심 로직이 들어가는 작업에 `설계 필요`를 표시한다. 그 작업은 구현 전에 `$hx-design`으로 선택지를 비교하고 사용자 결정을 받는다. 계획 단계에서 알고리즘을 미리 확정하지 않는다.

스택이 필요하면 제공 환경에 이미 있는 런타임·도구를 우선하고, 선택과 이유를 DECISIONS.md에 남긴다. 과제가 자료 분석·보고서형이면 웹앱을 덧붙이지 않는다.

## 승인과 진행
- PLAN.md에 저장한 뒤 핵심(MVP, 작업 순서, 완료 기준, 제외 범위)만 10줄 이내로 보여 주고 **사용자 승인을 기다린다.**
- 사용자가 고치면 PLAN.md에 반영하고 바뀐 점만 알린다.
- 승인 뒤에는 작업마다 묻지 않는다. 각 작업이 끝나면 `결과 / 검증 / 다음`을 보고하고, PLAN.md의 상태와 검증 결과만 갱신한 뒤 로컬 커밋한다.
- 전체 계획을 다시 출력하지 않는다.

후속 서술형 단계에서는 이 스킬을 쓰지 않는다.
